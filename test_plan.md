# UVM Test Plan — BLE CRC DUT

---

## 1. Objective

Verify that the BLE CRC DUT correctly computes the 24-bit BLE CRC for valid packet data streams, using the proper initialization value and bit processing order, across normal, boundary, and error-related scenarios.

---

## 2. DUT Description

The DUT is assumed to:

- Accept BLE packet bits or bytes as input
- Use a 24-bit CRC polynomial defined by BLE
- Support a configurable or fixed CRC initialization value
- Produce a 24-bit CRC result
- Optionally indicate completion with a valid/done signal

---

## 3. Verification Goals

The verification environment should confirm:

- Correct CRC generation for known BLE packet examples
- Correct handling of different payload lengths
- Correct handling of edge cases such as zero-length or minimum-length payloads
- Correct reset behavior
- Correct operation across randomized packet content
- Bit ordering and byte ordering match BLE spec expectations
- No unexpected state retention between transactions

---

## 4. Assumptions

This plan assumes the DUT interface includes some subset of:

| Signal | Description |
|--------|-------------|
| `clk` | System clock |
| `rst_n` | Active-low async reset |
| `start` | Begin new transaction and load init value |
| `data_in` | Input data byte |
| `data_valid` | Asserted when data_in is valid |
| `crc_init` | CRC seed value |
| `done` / `crc_valid` | Completion indicator |
| `crc_out` | CRC result output |

If the DUT is byte-based instead of bit-based, the same plan applies with adapted stimulus packing.

---

## 5. UVM Methodology

UVM (Universal Verification Methodology) is a standardized SystemVerilog framework for building reusable, structured testbenches. It defines a component hierarchy that separates stimulus generation, driving, monitoring, checking, and coverage into distinct layers.

Key concepts used in this plan:

| Component | Role |
|-----------|------|
| **Sequence item** | A transaction object holding one packet's payload, length, init value, and expected CRC |
| **Sequence** | Generates a stream of sequence items — directed or randomized |
| **Driver** | Consumes sequence items and drives the DUT interface cycle-by-cycle |
| **Monitor** | Passively observes the DUT interface and broadcasts observed transactions |
| **Scoreboard** | Receives transactions from the monitor, computes expected output via a reference model, and flags mismatches |
| **Coverage collector** | Samples coverpoints and crosses to measure which scenarios have been exercised |
| **Agent** | Bundles driver + monitor + sequencer into one reusable unit |
| **Env / Test** | Top-level integration — connects agents, scoreboard, and coverage; selects which sequences to run |

This testbench implements the same roles in module-based SystemVerilog using tasks and a covergroup rather than full UVM classes, which allows it to run on any SV simulator without a UVM library.

---

## 6. Testbench Architecture

### Stimulus

Stimulus is generated by tasks that map directly to UVM sequence/driver roles:

| Task | Purpose |
|------|---------|
| `send_packet` | Drive arbitrary payload bytes into DUT and verify CRC |
| `send_packet_init` | Same, but assert `start` + load `crc_init` seed first |
| `send_packet_with_gap` | Insert a 1-cycle `data_valid` gap mid-packet |
| `send_with_clear_overlap` | Assert `clear` simultaneously with `data_valid` deassertion |
| `test_mid_reset` | Assert `rst_n` mid-packet, then verify clean recovery |
| `do_clear` / `do_reset` / `do_start` | Utility helpers for reset and init control |

Directed phases cover every pattern × length combination explicitly. Phase 5 adds 30 randomized packets with 50% boundary-length bias (`len` ∈ {1, 2, 7, 8}) and occasional `rst_n` injection.

### Checking (Scoreboard)

`sw_crc()` is a pure SystemVerilog function that independently computes the BLE CRC-24 using the reflected polynomial `0xDA6000` and LSB-first bit ordering. Every task calls it after the packet completes and compares the result to `crc_out`. Mismatches are reported with payload, init value, expected, and actual CRC.

An `always @(posedge clk)` block also checks for X/Z on `crc_out` while `crc_valid=1` at runtime.

### Coverage

A single covergroup `cov_crc24` samples at every `posedge clk`. Module-level variables (`pkt_len_d`, `pkt_pattern`, `reset_scenario`) carry context from the stimulus tasks into the covergroup.

**9 coverpoints:**

| Coverpoint | Bins |
|------------|------|
| `cp_pkt_len` | 1 / 2–3 / 4–6 / 7–8 / 9–37 (BLE ADV PDU range) |
| `cp_data_in` | 0x00 / 0xFF / 0x01–0x7F / 0x80–0xFE |
| `cp_crc_out` | 0x000000 / 0xFFFFFF / other |
| `cp_rst_n` | in_reset / running |
| `cp_clear` | clearing / no_clear |
| `cp_crc_valid` | not_valid / asserted |
| `cp_init` | 0x555555 / 0x000000 / 0xFFFFFF / others |
| `cp_pattern` | zeros / ones / 0xAA / 0x55 / incrementing / other |
| `cp_reset_scenario` | idle_reset / between_txn / mid_txn / no_reset |

**5 cross coverpoints:**

| Cross | Bins | Notes |
|-------|------|-------|
| `cx_data_pktlen` | 4×5 = 20 | Every data range in every packet size |
| `cx_clear_valid` | 2×2 = 4 | Clear while CRC valid |
| `cx_pkt_pattern` | 5×6 = 30 | Every pattern in every length range |
| `cx_pkt_len_init` | 5×4 = 20 | Every length with every init seed |
| `cx_reset_txn` | 4×2 = 7 | Reset scenario × valid state; 1 `ignore_bins` for structurally impossible bin (`idle_reset × asserted`) |

## 7. Reference Model

A software golden model computes BLE CRC-24 independently from the DUT. It:

- Implements the BLE polynomial `0x00065B` in reflected form `0xDA6000`
- Processes bits LSB-first within each byte
- Accepts a configurable 24-bit initialization value
- Returns the expected CRC for scoreboard comparison

This is the key checker — every packet's expected output is derived from this model, not from DUT output.

---

## 8. Features to Verify

### 8.1 Reset
- CRC state resets correctly
- Outputs return to expected idle values
- Reset during idle behaves correctly
- Reset between transactions clears prior state

### 8.2 CRC Initialization
- Default CRC init is correct
- Programmed CRC init is correctly loaded
- Different init values affect output as expected

### 8.3 Payload Processing
- Single-byte payloads work
- Multi-byte payloads work
- Minimum and maximum supported payload sizes work
- All-zero, all-one, alternating, and random payload patterns work

### 8.4 Transaction Control
- `start` launches a new CRC calculation
- `crc_valid` asserts correctly
- Output CRC is stable when valid
- Back-to-back transactions work correctly

### 8.5 BLE-Specific Behavior
- BLE polynomial is correctly applied
- BLE bit ordering (LSB-first) is correct
- Packet bytes are consumed in the expected order
- CRC matches published BLE examples when available

## 9. Directed Test List

| Test | Description | Status |
|------|-------------|--------|
| **Test 1** — Reset Smoke Test | Confirm DUT resets; CRC clears, no false output | ✅ Phase 1 |
| **Test 2** — Single Known Packet | Compare DUT against one hand-checked BLE example; exact CRC match | ✅ Phase 3.5 |
| **Test 3** — Multiple Known Packets | All-zeros, all-ones, alternating (0xAA / 0x55), incrementing bytes | ✅ Phase 2 |
| **Test 4** — Zero-Length Payload | CRC from init-only state, if supported | ⚠️ Not supported by hardware |
| **Test 5** — Minimum Payload | Smallest legal BLE payload (1 byte) | ✅ Phase 2 |
| **Test 6** — Maximum Payload | Largest supported payload (37 bytes, BLE ADV PDU) | ✅ Phase 2 |
| **Test 7** — Different CRC Init Values | Multiple init seeds including 0x555555, 0x000000, 0xFFFFFF, arbitrary | ✅ Phase 3 |
| **Test 8** — Back-to-Back Transactions | No state leakage between packets | ✅ Phases 2–4 |
| **Test 9** — Mid-Transaction Reset | Reset during active CRC, then verify clean recovery | ✅ Phase 4 |
| **Test 10** — Random Payload Regression | 30 randomized packets with boundary-weighted lengths | ✅ Phase 5 |

---

## 10. Randomization Strategy

**Randomize:**
- Payload length
- Payload contents
- CRC init value
- Gap cycles between bytes (`data_valid` drops mid-packet)
- Back-to-back transaction spacing
- Occasional reset insertion between transactions

**Constraints:**
- Keep lengths within DUT-supported range (1–37)
- Bias 50% of iterations toward boundary lengths: 1, 2, 7, 8
- Zero-length excluded — not supported by hardware

---

## 11. Scoreboard Checks

For each transaction:
- Collect input payload and init value
- Compute expected CRC using `sw_crc()` reference model
- Compare with DUT `crc_out`
- Report mismatch with: payload, init value, expected CRC, actual CRC

Also check protocol behavior:
- `crc_valid` timing (SVA: `data_valid |=> crc_valid`, disabled during `rst_n` and `start`)
- No X/Z on `crc_out` while `crc_valid=1` (runtime `always` block + SVA `p_no_x_crc`)
- `crc_out` must be `0x000000` while `rst_n` is low (SVA `p_rst_output_zero`)

## 13. Pass/Fail Criteria

The DUT passes when:

- All directed tests pass
- Randomized regression completes with no mismatches
- Functional coverage reaches target:
  - 100% for key directed bins
  - 90%+ for overall functional coverage
- No unexpected protocol or timing violations occur

**Achieved: 100% overall functional coverage, zero scoreboard mismatches.**

---

## 14. Exit Criteria

Verification is complete when:

- All planned tests are implemented and passing
- Scoreboard shows zero unresolved mismatches
- All critical coverage bins are hit
- Known corner cases are exercised
- Any bugs found are fixed and regression-tested
